# Auditoria — Criptografia, Tokens e Máquina de Estados de Sessão

Escopo: `src/modules/auth/services/{password,opaque-token,access-token,sessions,pwned-passwords,refresh-cookie,action-tokens}.service.ts`, `src/modules/auth/strategies/jwt.strategy.ts`, `src/modules/auth/guards/origin.guard.ts`, `src/config/env.validation.ts`, `src/modules/auth/auth.service.ts`, `src/modules/auth/auth.controller.ts`.

Nenhum achado Critical/High/Medium confirmado nesta área. O módulo está bem implementado; abaixo, o que foi verificado linha a linha e duas observações Low/informativas.

## Categorias limpas (verificadas lendo o código real)

- **Hash de senha** (`password.service.ts:5-10,19-43`): Argon2**id** explícito (`argon2.argon2id`), `memoryCost: 19_456` (19 MiB), `timeCost: 2`, `parallelism: 1` — atende ao mínimo OWASP. `verify()` delega para `argon2.verify` (tempo constante da própria lib). `DUMMY_PASSWORD_HASH` é um hash argon2id real com os mesmos parâmetros, e `verifyDummy()` é de fato chamado em `auth.service.ts:178-180` para os status `'missing'` e `'locked'` — não há `if (!user) return` antes dele; o dummy roda depois da transação, fora do `if` que decide sucesso/erro, então usuário inexistente e usuário bloqueado pagam o mesmo custo de argon2 que uma senha errada real (que já rodou `passwords.verify` dentro da transação, linha 145-151).
- **Tokens opacos** (`opaque-token.service.ts`): `randomBytes(32)` (CSPRNG, 256 bits), codificado em base64url. Hash armazenado é SHA-256 (`createHash('sha256')`). Toda verificação (`sessions.service.ts`, `action-tokens.service.ts`) faz `findOne(..., { where: { tokenHash } })` — comparação é lookup por índice de hash no Postgres, não laço de comparação de string em JS.
- **Access token JWT** (`access-token.service.ts:21-33`, `jwt.strategy.ts:20-27`): algoritmo fixado explicitamente nos dois lados (`algorithm/algorithms: ['HS256']` — array, não string solta), sem suporte a `alg: none` ou confusão RS/HS. `issuer` e `audience` são exigidos tanto na emissão quanto na verificação via `passport-jwt` (`issuer`, `audience` no `super()`), não apenas emitidos. Payload contém somente `{ sid }` + `sub` (userId) + claims padrão — nenhum PII (sem email/role). A strategy (`jwt.strategy.ts:30-40`) valida `sub`/`sid` como UUID e chama `sessions.validateActiveSession`, que consulta o banco (`sessions.service.ts:227-250`) exigindo `revokedAt IS NULL` e `expiresAt > now`, além de buscar o usuário — logout e expiração de sessão realmente invalidam o access token antes do seu próprio TTL expirar.
- **`JWT_SECRET` ausente/curto** (`env.validation.ts:65-70`): `REQUIRED_KEYS` inclui `JWT_SECRET`; validação adicional exige ≥32 bytes e rejeita padrões de placeholder (`replace`, `placeholder`, `change-me`). `validateEnvironment` é passado como `validate` do `ConfigModule.forRoot` (`app.module.ts:20`), portanto o Nest lança exceção na inicialização do módulo — boot falha fail-closed, sem fallback inseguro. `AccessTokenService`/`JwtStrategy` também usam `config.getOrThrow`, então mesmo que a validação de boot fosse contornada, a ausência da chave lançaria em runtime em vez de usar um valor padrão.
- **Rotação de refresh token / reuso** (`sessions.service.ts:87-187`): o fluxo de refresh busca o token sem lock primeiro só para descobrir IDs, mas a decisão real acontece depois de adquirir `pessimistic_write` em `user`, depois em `session`, depois no próprio `current` (linhas 108-137) — a checagem de `usedAt`/`revokedAt` (linha 139) só é lida sob lock, então duas chamadas de refresh concorrentes com o mesmo token serializam: a segunda vê `usedAt` já setado pela primeira e cai no ramo de reuso, que revoga a sessão inteira e todos os refresh tokens dela (`revokeWithManager`, linhas 264-278) — não é um TOCTOU. Token expirado ou já revogado é rejeitado (linhas 139-153, cobre também sessão expirada/revogada). `logout` (linhas 189-225) revoga a sessão com o mesmo padrão de locks, e como a `JwtStrategy` consulta a sessão a cada requisição, o access token para de funcionar mesmo antes de expirar. `resetPassword` (`action-tokens.service.ts:189`) chama `sessions.revokeAllWithManager`, revogando todas as sessões do usuário dentro da mesma transação que troca a senha.
- **Cookie de refresh** (`refresh-cookie.service.ts`): `httpOnly: true`, `secure` verdadeiro sempre que `NODE_ENV !== 'development'` (cobre produção e teste), `sameSite: 'strict'`, `path: '/auth'` (restrito), sem `domain` (host-only). `maxAge` calculado a partir de `refreshExpiresAt - now`, alinhado ao TTL da sessão (`SESSION_TTL_MS`, 30 dias). Conferido em `auth.controller.ts`: o `refreshToken` só é escrito no cookie via `setRefreshCookie`; a resposta JSON (`toResponse`, linhas 153-160) expõe apenas `accessToken/tokenType/expiresIn/user` — o refresh token bruto nunca vai no corpo.
- **Guard de Origin** (`origin.guard.ts`): compara `request.headers.origin !== this.allowedOrigin` — igualdade estrita contra a origin exata derivada de `FRONTEND_URL` (via `new URL(...).origin`), não `startsWith`/`includes`, então `https://app.example.com.attacker.tld` é rejeitado (confirmado também pelo teste em `origin.guard.spec.ts:37-39`). Fora de produção o guard sempre libera (`!this.isProduction { return true }`), o que é aceitável para dev/test mas significa que, se `NODE_ENV` for mal configurado em um ambiente exposto, o guard vira no-op — depende inteiramente da corretude de `NODE_ENV`. Em produção, `Origin` ausente é negado (fail-closed), confirmado pelo teste `origin.guard.spec.ts:42-46`.
- **Verificação de senha vazada** (`pwned-passwords.service.ts`): usa k-anonimato correto — só os 5 primeiros chars do SHA-1 vão na URL (`/range/${prefix}`), a senha completa e o SHA-1 completo nunca saem da máquina; a comparação do sufixo acontece localmente. Falha de rede, timeout ou resposta não-OK resultam em `ServiceUnavailableException` — comportamento fail-closed (bloqueia registro/reset se a API do HIBP estiver indisponível).

## Observações Low / informativas (não são vulnerabilidades)

```
## Achado: Fail-closed do HIBP é uma escolha de disponibilidade, não um bug
**Severidade:** Low
**Confiança:** Alta
**Verificado como:** pwned-passwords.service.ts:37-48 — qualquer erro (timeout, rede, HTTP não-OK) lança ServiceUnavailableException, que propaga e bloqueia register/reset-password inteiramente.
**Impacto:** Se a API pwnedpasswords.com estiver fora do ar ou um firewall bloquear o egress, ninguém consegue se registrar ou resetar senha (negação de serviço indireta). Do ponto de vista de segurança, fail-closed é a escolha correta (evita aceitar senha comprometida quando a checagem não pôde ser feita); é uma decisão consciente de trade-off segurança-vs-disponibilidade, não um defeito.
**Correção:** Nenhuma ação obrigatória. Se disponibilidade for prioridade, considerar circuit breaker/cache de resultados recentes, mas isso é decisão de produto, não achado de segurança.
```

```
## Achado: Reuso de refresh token expirado naturalmente também revoga a sessão inteira
**Severidade:** Low
**Confiança:** Alta
**Verificado como:** sessions.service.ts:144-153 — o mesmo branch que trata expiração natural do token (`current.expiresAt.getTime() <= now.getTime()`) chama `revokeWithManager(manager, session, now)`, igual ao branch de reuso malicioso (linhas 139-142).
**Impacto:** Nenhum impacto de segurança — é mais estrito que o necessário (um usuário que deixa o token expirar naturalmente perde a sessão inteira, exigindo novo login, em vez de só aquele refresh falhar). Não é explorável; é uma escolha conservadora.
**Correção:** Nenhuma ação necessária; opcionalmente diferenciar UX entre "expirado" e "reuso detectado" se o produto quiser reduzir re-logins desnecessários.
```
